# SoundBox — PLAN

## Выбранный базовый вариант

**Вариант A: LSB-стеганография в несжатом аудио.**

В качестве основного формата используется:

```text
WAV / PCM 16-bit little-endian
```

MP3 напрямую для LSB-встраивания не используется, потому что это формат со сжатием без сохранения исходных сэмплов. После перекодирования в MP3 скрытые данные почти гарантированно будут уничтожены.

Для работы с MP3-источниками рекомендуется предварительная конвертация:

```
ffmpeg -i input.mp3 -c:a pcm_s16le -ar 44100 -ac 2 input.wav
```

Дальше файл `input.wav` обрабатывается как обычный несжатый аудиофайл.Текущая цель проекта

## Текущая цель проекта

Сделать простой и понятный аналог `stegobox`, но для аудио:

- вход: аудиофайл WAV;
- скрытие текста в младших битах 16-битных сэмплов;
- шифрование текста перед встраиванием;
- извлечение текста по паролю;
- сохранение результата в новый WAV-файл;
- визуальный интерфейс на Swing + FlatLaf.

## Архитектурная схема

```
AudioFrame
   │
   ├── выбор аудиофайла
   ├── ввод текста
   ├── ввод пароля
   ├── отображение ёмкости
   └── отображение статуса
        │
        ▼
AudioEngine
   │
   ├── loadPcm()
   ├── hideText()
   ├── extractText()
   ├── writeWav()
   ├── capacityBytes()
   └── payloadSize()
```

Принцип разделения тот же, что и в `stegobox`:

```
UI ничего не знает о криптографии и встраивании.
Движок ничего не знает о Swing.
```

- асинхронная обработка через `SwingWorker`

## Формат скрытых данных

```
[4 байта: длина payload] [payload]
```

`payload`:

```
[16 байт salt][12 байт IV][шифротекст + 16 байт GCM-тега]
```

Общий служебный overhead:

```
4 + 16 + 12 + 16 = 48 байт
```

## Метод встраивания

Используется 16-битный PCM.

Один сэмпл занимает 2 байта:

```
16-bit sample = 2 bytes
```

Мы прячем 1 бит в младший бит каждого сэмпла.

Ёмкость:

```
capacity_bytes = pcm_bytes / 16
```

Пояснение:

```
pcm_bytes / 2     = количество сэмплов
количество сэмплов / 8 = количество байт полезной нагрузки
итого:
pcm_bytes / 16
```

Пример:

```
44.1 kHz
16 bit
stereo
```

Поток:

```
44100 × 2 канала × 2 байта = 176400 байт/сек
```

Скрытая ёмкость:

```
176400 / 16 = 11025 байт/сек
```

Примерно:

```
10.8 КБ в секунду
```

## Этап 2. Клиентский режим

Цель: сделать полноценный консольный режим по аналогии со `stegobox`.

CLI должен поддерживаться автоматически:

```
если есть аргументы командной строки — работает CLI;
если аргументов нет — открывается GUI.
```

Ожидаемый файл:

```
src/main/java/ru/mcs/Cli.java
```

Использование в `Main.java`:

```
if (args.length > 0) {
    System.exit(Cli.run(args));
}
```

## Планируемый CLI

Команды:

```
soundbox hide    -i <audio> -t <text> | --text-file <file> -p <password> [-o <out>]
soundbox extract -i <audio> -p <password> [-o <out.txt>]
soundbox help
soundbox version
```

### Примеры

Скрыть строку:

```
soundbox hide -i audio.wav -t "секрет" -p password
```

Скрыть текст из файла:

```
soundbox hide -i audio.wav --text-file secret.txt -p password
```

Скрыть текст из stdin:

```
cat secret.txt | soundbox hide -i audio.wav -t - -p password
```

Извлечь в stdout:

```
soundbox extract -i audio_stego.wav -p password
```

Извлечь в файл:

```
soundbox extract -i audio_stego.wav -p password -o secret.txt
```

## Планируемые параметры CLI

### Общие

```
-i, --input <file>
    входной аудиофайл

-p, --password <password>
    пароль

-o, --output <file>
    выходной файл
```

Если `--output` не указан:

для `hide`:

- по умолчанию создаётся файл рядом с исходником:

  ```
  <имя>_stego.wav
  ```

- для `extract`:
  
  - текст выводится в `stdout`.

### Только для `hide`

```
-t, --text <text>
    текст для сокрытия

--text-file <file>
    прочитать текст из файла UTF-8
```

Если указать:

```
-t -
```

то текст читается из `stdin`.

## Планируемое поведение пароля в CLI

Порядок получения пароля:

1. параметр:

```
   --password
```

1. переменная окружения:

```
   SOUNDBOX_PASSWORD
```

1. интерактивный ввод через:

```
   System.console().readPassword()
```

После использования массив пароля должен затираться:

```
Arrays.fill(password, '\0');
```


Примеры ошибок использования:

- неизвестная команда.

## Этап 4. Отношение к MP3

Для текущего проекта выбирается следующий подход:

```
MP3 → WAV → LSB → WAV
```

Прямое скрытие в битпоток `.mp3` в текущем этапе не делаем.

Причины:

- MP3 использует психоакустическую модель и сжатие с потерями;
- младшие биты PCM не переживают повторное кодирование в MP3;
- правка произвольных байтов внутри `.mp3` может сломать файл;
- без аудио-библиотек полноценная работа с MP3 в Java сложнее.

Возможный будущий отдельный вариант:

```
Вариант B: размещение зашифрованного пакета в метаданных аудиофайла,
например, в ID3v2 PRIV frame для MP3.
```

Это не является частью текущего этапа и может быть вынесено в отдельную задачу.

# Вариант C. Robust audio steganography

Отдельное исследовательское направление.

Цель:

```
Найти и прототипировать методы скрытия текста в аудио,
устойчивые к сжатию, перекодированию и базовым обработкам.
```

Этот вариант не входит в текущий основной план реализации. Он будет исследоваться отдельно.

## Направления исследования

### 1. Spread spectrum

Идея:

- полезная нагрузка распределяется по широкой части аудиосигнала;
- используется псевдослучайная последовательность;
- извлечение возможно при наличии ключа/последовательности.

Плюсы:

- лучшая устойчивость к шуму и сжатию;
- сложнее обнаружить без ключа.

Минусы:

- ниже ёмкость;
- сложнее реализация;
- нужны тесты на качество звука.

### 2. Phase coding

Идея:

- информация прячется в фазовых характеристиках сегментов сигнала.

Плюсы:

- потенциально хорошая устойчивость к некоторым преобразованиям;
- может быть менее заметной на слух.

Минусы:

- требует аккуратной работы с фазой;
- возможны артефакты;
- сложность синхронизации и извлечения.

### 3. Echo hiding

Идея:

- информация кодируется параметрами искусственного эха:
  - задержка;
  - амплитуда;
  - время затухания.

Плюсы:

- концептуально простой метод;
- может быть устойчив к некоторым обработкам.

Минусы:

- низкая ёмкость;
- заметность эха при неправильных параметрах;
- ограниченная применимость для разных типов музыки/речи.

### 4. DCT/DWT-based methods

Идея:

- аудио разбивается на блоки;
- применяется дискретное косинусное или вейвлет-преобразование;
- данные прячутся в коэффициентах преобразования;
- возможно использование quantization index modulation (QIM).

Плюсы:

- ближе к алгоритмам, устойчивым к сжатию;
- можно выбирать частотные области с меньшей чувствительностью;
- хорошо подходит для исследований.

Минусы:

- самая сложная реализация;
- нужно тщательно подбирать параметры;
- необходимы тесты после кодирования в MP3/OGG/AAC.

## Метрики для сравнения методов

### Ёмкость

```
сколько байт можно спрятать в 1 минуту аудио
```

### Незаметность

Возможные метрики:

```
SNR
PSNR
PEAQ
субъективное прослушивание
```

### Устойчивость

Проверки:

```
после сохранения в MP3 128 kbps
после сохранения в MP3 192 kbps
после сохранения в MP3 320 kbps
после изменения громкости
после ресемплирования
после обрезки
после добавления шума
```

### Надёжность извлечения

```
BER — bit error rate
```

Нужно понять, можно ли восстановить полный зашифрованный пакет после обработки.
